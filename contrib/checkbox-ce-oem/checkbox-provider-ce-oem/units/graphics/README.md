# OpenCL Graphics Tests

The OpenCL graphics tests validate OpenCL platform and device availability and
properties using `clinfo`. The resource job discovers platform/device pairs and
generates one validation job per eligible pair.

## Test plan

The generated jobs are included by `ce-oem-graphics-automated` through the
`opencl_clinfo_resource` bootstrap resource. The
`ce-oem-graphics/opencl-property-validation` template also uses
`flags: also-after-suspend`, so Checkbox can generate before-suspend and
after-suspend variants for suspend flows.

## Manifest

Enable the manifest gate before running the generated jobs:

```text
has_opencl_support: True
```

If this manifest value is not `True`, the OpenCL detect and validation jobs are
not selected.

## Jobs

### `ce-oem-graphics/detect_opencl`

Checks that `clinfo` is available and that at least one OpenCL platform and
device pair can be listed. This job fails if no platform is found (OpenCL
runtime not installed) or if a platform is found but no device is usable.

#### Scenario: Pass

Have at least 1 platform and 1 device pair like below.

```bash
ubuntu@ubuntu:~$ clinfo -l
Platform #0: ARM Platform
`-- Device #0: Mali-G57 r0p1
```
#### Scenario: Fail

1. No any platform & device (It's because the OpenCL Runtime is not installed)

```bash
ubuntu@ubuntu:~$ clinfo -l
```

2. Have a platform without any device (The OpenCL Runtime is installed, but no usable devices)

```bash
ubuntu@ubuntu:~$ clinfo -l
Platform #0: rusticl
```

### `opencl_clinfo_resource`

Runs `clinfo -l` to enumerate all OpenCL platform/device pairs and emits
Checkbox resource records. Each record contains:

| Field | Description |
| --- | --- |
| `platform` | OpenCL platform name |
| `platform_number` | Platform index reported by `clinfo` |
| `device` | OpenCL device name |
| `device_number` | Device index reported by `clinfo` |
| `ignore` | `true` if the pair is listed in `ignored_set`; `false` otherwise |

Records where `ignore` is `true` are filtered out by the template and do not
produce validation jobs.

#### Example

```
platform: ARM Platform
platform_number: 0
device: Mali-G57 r0p0
device_number: 0
ignore: false

platform: Portable Computing Language
platform_number: 1
device: cpu--cortex-a55
device_number: 0
ignore: true
```

### `ce-oem-graphics/opencl-property-validation-{{platform_number}}-{{device_number}}`

Generated by the `ce-oem-graphics/opencl-property-validation` template for
each non-ignored platform/device pair. Validates a set of OpenCL device
properties using `clinfo -d <platform_number>:<device_number> --prop <property>`.

The default validated properties are:

| Property | Expected value |
| --- | --- |
| `CL_DEVICE_AVAILABLE` | `CL_TRUE` |
| `CL_DEVICE_COMPILER_AVAILABLE` | `CL_TRUE` |
| `CL_DEVICE_EXECUTION_CAPABILITIES` | `CL_EXEC_KERNEL` |

Additional properties can be added per platform/device pair through
`CLINFO_VALIDATION_JSON_FILE` (see below).

## Environment variables

Use these variables in the launcher `[environment]` section when needed:

| Variable | Description | Default |
| --- | --- | --- |
| `EXECUTABLE_JSON_PATH` | Path to a JSON file that overrides the `clinfo` executable or prepends library paths. | Not set |
| `CLINFO_VALIDATION_JSON_FILE` | Path to a JSON file that defines ignored platform/device pairs and extended property validations. | Not set |

### `EXECUTABLE_JSON_PATH`

Points to a JSON file that controls how the `clinfo` binary is resolved. If not
set, the system `clinfo` on `PATH` is used. When set, the file is read and the
`clinfo` key determines how the command is assembled.

If the path is relative, it is resolved under `PLAINBOX_PROVIDER_DATA`.

**Format:**

```json
{
  "clinfo": {
    "LD_PATH": ["/path/to/lib1", "/path/to/lib2"],
    "env1": "value1"
  }
}
```

- `LD_PATH` prepends entries to `LD_LIBRARY_PATH` before the command is run.
- Any other key/value pair is prepended as an environment variable assignment.
- If the `clinfo` key is absent from the file, the default system `clinfo` is
  used unchanged.

### `CLINFO_VALIDATION_JSON_FILE`

Points to a JSON file with two optional sections: `ignored_set` and
`customized_validation_set`.

**Format:**

```json
{
  "ignored_set": {
    "<Platform Name>": ["<Device Name 1>", "<Device Name 2>"]
  },
  "customized_validation_set": {
    "<Platform Name>": {
      "<Device Name>": {
        "<CL_PROPERTY>": "<expected value>"
      }
    }
  }
}
```

- `ignored_set` — platform/device pairs listed here will have `ignore: true`
  in the resource output and will not produce validation jobs.
- `customized_validation_set` — extends (not replaces) the default validation
  set for a specific platform/device pair. Properties defined here are added
  to the three default properties that are always validated.

**Example:**

```json
{
  "ignored_set": {
    "ARM Platform": ["FooBar 9999"]
  },
  "customized_validation_set": {
    "ARM Platform": {
      "Mali-G57 r0p0": {
        "CL_DEVICE_MAX_COMPUTE_UNITS": "2",
        "CL_DEVICE_MAX_WORK_GROUP_SIZE": "512",
        "CL_DEVICE_VENDOR_ID": "0x13b5"
      }
    }
  }
}
```

In this example:

- The `ignored_set` entry causes the pair platform `ARM Platform` / device
  `FooBar 9999` to be skipped. The resource job emits `ignore: true` for that
  pair, so the template does not generate a validation job for it.
- The `customized_validation_set` entry extends the validation for platform
  `ARM Platform` / device `Mali-G57 r0p0`. In addition to the three default
  properties (`CL_DEVICE_AVAILABLE`, `CL_DEVICE_COMPILER_AVAILABLE`,
  `CL_DEVICE_EXECUTION_CAPABILITIES`), the validation job also checks
  `CL_DEVICE_MAX_COMPUTE_UNITS`, `CL_DEVICE_MAX_WORK_GROUP_SIZE`, and
  `CL_DEVICE_VENDOR_ID` against the values defined here.

## Running the jobs

After setting the manifest and environment, run the automated graphics plan:

```bash
checkbox-ce-oem.checkbox-cli run com.canonical.contrib::ce-oem-graphics-automated
```

The detect job uses `clinfo_test.py detect` to confirm at least one
platform/device pair is available. The resource job uses
`clinfo_test.py resource` to generate per-pair records. Each generated
validation job uses `clinfo_test.py test` to query and compare device
properties against the expected values.

A job fails if `clinfo` cannot be executed, no OpenCL platform or device is
found, a queried property is missing from the output, or a property value does
not match the expected value.

# Vulkan Graphics Tests

The Vulkan graphics tests validate that the Vulkan stack works correctly on
each hardware GPU device using `vulkaninfo`. The resource job discovers
hardware GPU devices and generates one validation job per device.

## Test plan

The generated jobs are included by `ce-oem-graphics-automated` through the
`vulkan_vulkaninfo_resource` bootstrap resource. The
`ce-oem-graphics/vulkan-vulkaninfo-device-validation` template also uses
`flags: also-after-suspend`, so Checkbox can generate before-suspend and
after-suspend variants for suspend flows.

## Manifest

Enable the manifest gate before running the generated jobs:

```text
has_vulkan_support: True
```

If this manifest value is not `True`, the Vulkan resource and validation jobs
are not selected.

## Jobs

### `vulkan_vulkaninfo_resource`

Runs `vulkaninfo --summary` and emits one Checkbox resource record per
hardware GPU device (`deviceType` `DISCRETE_GPU` or `INTEGRATED_GPU`).
Software-only devices, such as Mesa's llvmpipe/lavapipe CPU device, are never
emitted. Each record contains:

| Field | Description |
| --- | --- |
| `device_number` | GPU index reported by `vulkaninfo` (the `GPUn` block number) |
| `device_name` | GPU device name (`deviceName`) |

#### Example

On a multi-GPU system, `vulkaninfo --summary` lists every device (real
hardware and software fallback) in the same output, but only hardware devices
are emitted as resource records:

```
device_number: 0
device_name: Intel(R) Graphics (LNL)
```

### `ce-oem-graphics/check-vulkan_vulkaninfo_resource`

Checks that the `vulkan_vulkaninfo_resource` resource job command executes
directly and finds at least one hardware GPU device. This job fails if
`vulkaninfo` cannot be executed or no hardware GPU device is reported.

### `ce-oem-graphics/vulkan-vulkaninfo-device-validation-GPU{{device_number}}`

Generated by the `ce-oem-graphics/vulkan-vulkaninfo-device-validation`
template for each hardware GPU device found by `vulkan_vulkaninfo_resource`.
Validates the Vulkan stack for that device by running
`vulkaninfo --summary` and checking:

1. There is output at all — no output means the command failed to produce a
   report.
2. The command exits with code `0`. A crash inside the driver (e.g. a
   segmentation fault) kills the process with a signal and is reported as a
   negative return code (e.g. `-11`).
3. No software renderer (`llvmpipe`, `softpipe`, `swrast`) is reported for
   this device's own `GPU{{device_number}}:` block.

On multi-GPU systems, `vulkaninfo --summary` lists every device in one
combined output. Criterion 3 is scoped to this device's own block, so an
unrelated software-only device listed elsewhere in the output (e.g. Mesa's
llvmpipe fallback alongside a real GPU) doesn't fail this device's job.
Criteria 1 and 2 always apply to the whole output, since a crash or empty
output means no device-specific block exists at all.

#### Scenario: Pass

The command exits with code `0` and the device's block reports a real
hardware renderer:

```
GPU0:
	apiVersion         = 1.4.303 (4210991)
	driverVersion      = 1.0.0
	vendorID           = 0x8086
	deviceID           = 0x64a0
	deviceType         = PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU
	deviceName         = Intel(R) Graphics (LNL)
```

#### Scenario: Fail

1. No output at all (e.g. `vulkaninfo` is not installed or crashes before
   producing any text).

2. `vulkaninfo` exits non-zero or is killed by a signal, e.g. a segfault in
   the GPU driver:

```
FAIL: ['vulkaninfo', '--summary'] exited with returncode -11
```

3. A software renderer is reported for the target device's block:

```
GPU1:
	deviceType         = PHYSICAL_DEVICE_TYPE_CPU
	deviceName         = llvmpipe (LLVM 15.0.7, 256 bits)
```

## Environment variables

Use these variables in the launcher `[environment]` section when needed:

| Variable | Description | Default |
| --- | --- | --- |
| `CUSTOM_VULKAN_COMMAND_PATH` | `vulkaninfo` executable to run (name on `PATH` or absolute path). | `vulkaninfo` |
| `VK_ICD_FILENAMES` | Vulkan ICD manifest(s) the loader must use. | Not set |
| `VULKANINFO_LD_LIBRARY_PATH` | `LD_LIBRARY_PATH` to run `vulkaninfo` with. | Not set |

### `VULKANINFO_LD_LIBRARY_PATH`

`vulkaninfo` is run **without** the `LD_LIBRARY_PATH` inherited from
Checkbox, which in the Checkbox snap points at the Checkbox runtime
libraries. A launcher `LD_LIBRARY_PATH` cannot be used instead, because
Checkbox never overrides a variable that is already set. Set
`VULKANINFO_LD_LIBRARY_PATH` only if the host GPU libraries are not found
through `ld.so.conf`, e.g.:

```text
VULKANINFO_LD_LIBRARY_PATH=/opt/<vendor>/lib/aarch64-linux-gnu
```

### `VK_ICD_FILENAMES` with the snap

`VK_ICD_FILENAMES` is read by the loader *inside* the snap, so it must be a
path visible in the snap's namespace, not a host path such as
`/usr/share/vulkan/icd.d/mali.json`. For example, on Genio (Mali):

| Image | `VK_ICD_FILENAMES` |
| --- | --- |
| Ubuntu Core | ICD shipped in the snap, e.g. `/snap/<vulkan-snap>/current/<icd-dir>/mali_icd.json` |
| Classic (host driver) | ICD the snap generates from the host one, e.g. `/root/snap/<vulkan-snap>/common/<icd-dir>/mali.json` |
| Classic, host `vulkaninfo` deb | `/usr/share/vulkan/icd.d/mali.json` |


`VK_ICD_FILENAMES` is usually optional with a snap that only registers
vendor ICDs (no Mesa `gfxstream`/`virtio` ICDs that hang or crash on Genio);
an unusable ICD is just skipped by the loader.

## Running the jobs

After setting the manifest and environment, run the automated graphics plan:

```bash
checkbox-ce-oem.checkbox-cli run com.canonical.contrib::ce-oem-graphics-automated
```

The resource job uses `vulkaninfo_test.py resource` to discover hardware GPU
devices. The check job uses `vulkaninfo_test.py resource` directly to confirm
at least one hardware GPU device is found. Each generated validation job uses
`vulkaninfo_test.py test -dn <device_number> -n <device_name>` to validate
the Vulkan stack for that specific device.

A job fails if `vulkaninfo` cannot be executed, produces no output, produces
crash/unexpected output, or reports a software renderer for the target
device.

# OpenGL Graphics Tests

The OpenGL graphics tests validate EGL platform initialization and rendering
using `eglinfo`. The resource job always emits a fixed set of platforms
(GBM, Wayland, X11, Surfaceless), and a validation job is generated per
platform that is not ignored.

## Test plan

The generated jobs are included by `ce-oem-graphics-automated` through the
`opengl_eglinfo_resource` bootstrap resource. The
`ce-oem-graphics/opengl-eglinfo-platform-validation` template also uses
`flags: also-after-suspend`, so Checkbox can generate before-suspend and
after-suspend variants for suspend flows.

## Manifest

Enable the manifest gate before running the check and validation jobs:

```text
has_opengl_support: True
```

If this manifest value is not `True`, the
`ce-oem-graphics/check-opengl_eglinfo_resource` job and the generated
`ce-oem-graphics/opengl-platform-validation-{{platform_name}}` jobs are not
selected. The `opengl_eglinfo_resource` resource job itself is not gated by the
manifest, since it must run during bootstrap to populate the template.

## Jobs

### `opengl_eglinfo_resource`

Emits one record for each platform in the fixed set (`gbm`, `wayland`, `x11`,
`surfaceless`). Platform support is not auto-detected; every platform is
always emitted, and only the `EGLINFO_IGNORED_PLATFORM` environment variable
(see below) controls whether a platform is ignored. Each record contains:

| Field | Description |
| --- | --- |
| `platform_name` | Platform key passed to `eglinfo -p` (e.g. `gbm`) |
| `ignore` | `true` if `platform_name` is listed in `EGLINFO_IGNORED_PLATFORM`; `false` otherwise |

Records where `ignore` is `true` are filtered out by the template and do not
produce validation jobs.

#### Example

```
platform_name: gbm
ignore: false

platform_name: x11
ignore: true
```

### `ce-oem-graphics/check-opengl_eglinfo_resource`

Verifies that the OpenGL eglinfo resource generation command executes
directly.

### `ce-oem-graphics/opengl-platform-validation-{{platform_name}}`

Generated by the `ce-oem-graphics/opengl-eglinfo-platform-validation` template
for each non-ignored platform. Runs `eglinfo -B -p <platform_name>` and
applies the following judgement criteria, in order:

1. No output at all -> fail.
2. `eglInitialize failed` found in the output -> fail.
3. A software renderer (`llvmpipe`, `softpipe`, or `swrast`) is observed in
   the output -> fail.

Otherwise, the job passes.

#### Scenario: Pass

```bash
ubuntu@ubuntu:~$ eglinfo -B -p gbm
...
OpenGL renderer string: Mali-G715
...
```

#### Scenario: Fail

1. No output (`eglinfo` not found, or crashed before printing anything)

```bash
ubuntu@ubuntu:~$ eglinfo -B -p x11
```

2. EGL failed to initialize for the platform

```bash
ubuntu@ubuntu:~$ eglinfo -B -p x11
eglInitialize failed
```

3. EGL initialized, but rendering falls back to a software renderer

```bash
ubuntu@ubuntu:~$ eglinfo -B -p surfaceless
...
OpenGL renderer string: llvmpipe (LLVM 15.0.0, 256 bits)
...
```

## Environment variables

Use these variables in the launcher `[environment]` section when needed:

| Variable | Description | Default |
| --- | --- | --- |
| `EXECUTABLE_JSON_PATH` | Path to a JSON file that overrides the `eglinfo` executable or prepends library paths. | Not set |
| `EGLINFO_IGNORED_PLATFORM` | Comma-separated list of platform names to ignore. | Not set |

### `EXECUTABLE_JSON_PATH`

Points to a JSON file that controls how the `eglinfo` binary is resolved. If
not set, the system `eglinfo` on `PATH` is used. When set, the file is read
and the `eglinfo` key determines how the command is assembled.

If the path is relative, it is resolved under `PLAINBOX_PROVIDER_DATA`.

**Format:**

```json
{
  "eglinfo": {
    "LD_PATH": ["/path/to/lib1", "/path/to/lib2"],
    "env1": "value1"
  }
}
```

- `LD_PATH` prepends entries to `LD_LIBRARY_PATH` before the command is run.
- Any other key/value pair is prepended as an environment variable assignment.
- If the `eglinfo` key is absent from the file, the default system `eglinfo`
  is used unchanged.

### `EGLINFO_IGNORED_PLATFORM`

A comma-separated list of platform names that should be marked `ignore: true`
by the resource job and skipped by the validation template. Valid names are
`gbm`, `wayland`, `x11`, and `surfaceless`. Names are matched
case-insensitively, and surrounding whitespace is ignored.

**Example:**

```text
EGLINFO_IGNORED_PLATFORM=x11,surfaceless
```

In this example, the resource job emits `ignore: true` for the `x11` and
`surfaceless` platforms, so the template does not generate validation jobs
for them. The `gbm` and `wayland` platforms are unaffected and still produce
validation jobs.

## Running the jobs

After setting the manifest and environment, run the automated graphics plan:

```bash
checkbox-ce-oem.checkbox-cli run com.canonical.contrib::ce-oem-graphics-automated
```

The resource job uses `eglinfo_test.py resource` to emit the fixed set of
platform records. Each generated validation job uses
`eglinfo_test.py test -p <platform_name>` to run `eglinfo` for that platform
and check its output against the judgement criteria described above.

A job fails if `eglinfo` cannot be executed, produces no output, reports
`eglInitialize failed`, or falls back to a software renderer.
