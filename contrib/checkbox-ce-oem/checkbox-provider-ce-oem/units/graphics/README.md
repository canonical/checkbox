# OpenCL Graphics Tests

The OpenCL graphics tests validate OpenCL platform and device availability and
properties using `clinfo`. The resource job discovers platform/device pairs and
generates one validation job per eligible pair.

## Test plan

The generated jobs are included by `ce-oem-graphics-automated` through the
`opencl_clinfo_resource` bootstrap resource. The
`ce-oem-graphics/opencl-property-validation` template also uses
`flags: also-after-suspend`, so Checkbox can generate before-suspend and
after-suspend variants for suspend flows.

## Manifest

Enable the manifest gate before running the generated jobs:

```text
has_opencl_support: True
```

If this manifest value is not `True`, the OpenCL detect and validation jobs are
not selected.

## Jobs

### `ce-oem-graphics/detect_opencl`

Checks that `clinfo` is available and that at least one OpenCL platform and
device pair can be listed. This job fails if no platform is found (OpenCL
runtime not installed) or if a platform is found but no device is usable.

#### Scenario: Pass

Have at least 1 platform and 1 device pair like below.

```bash
ubuntu@ubuntu:~$ clinfo -l
Platform #0: ARM Platform
`-- Device #0: Mali-G57 r0p1
```
#### Scenario: Fail

1. No any platform & device (It's because the OpenCL Runtime is not installed)

```bash
ubuntu@ubuntu:~$ clinfo -l
```

2. Have a platform without any device (The OpenCL Runtime is installed, but no usable devices)

```bash
ubuntu@ubuntu:~$ clinfo -l
Platform #0: rusticl
```

### `opencl_clinfo_resource`

Runs `clinfo -l` to enumerate all OpenCL platform/device pairs and emits
Checkbox resource records. Each record contains:

| Field | Description |
| --- | --- |
| `platform` | OpenCL platform name |
| `platform_number` | Platform index reported by `clinfo` |
| `device` | OpenCL device name |
| `device_number` | Device index reported by `clinfo` |
| `ignore` | `true` if the pair is listed in `ignored_set`; `false` otherwise |

Records where `ignore` is `true` are filtered out by the template and do not
produce validation jobs.

#### Example

```
platform: ARM Platform
platform_number: 0
device: Mali-G57 r0p0
device_number: 0
ignore: false

platform: Portable Computing Language
platform_number: 1
device: cpu--cortex-a55
device_number: 0
ignore: true
```

### `ce-oem-graphics/opencl-property-validation-{{platform_number}}-{{device_number}}`

Generated by the `ce-oem-graphics/opencl-property-validation` template for
each non-ignored platform/device pair. Validates a set of OpenCL device
properties using `clinfo -d <platform_number>:<device_number> --prop <property>`.

The default validated properties are:

| Property | Expected value |
| --- | --- |
| `CL_DEVICE_AVAILABLE` | `CL_TRUE` |
| `CL_DEVICE_COMPILER_AVAILABLE` | `CL_TRUE` |
| `CL_DEVICE_EXECUTION_CAPABILITIES` | `CL_EXEC_KERNEL` |

Additional properties can be added per platform/device pair through
`CLINFO_VALIDATION_JSON_FILE` (see below).

## Environment variables

Use these variables in the launcher `[environment]` section when needed:

| Variable | Description | Default |
| --- | --- | --- |
| `EXECUTABLE_JSON_PATH` | Path to a JSON file that overrides the `clinfo` executable or prepends library paths. | Not set |
| `CLINFO_VALIDATION_JSON_FILE` | Path to a JSON file that defines ignored platform/device pairs and extended property validations. | Not set |

### `EXECUTABLE_JSON_PATH`

Points to a JSON file that controls how the `clinfo` binary is resolved. If not
set, the system `clinfo` on `PATH` is used. When set, the file is read and the
`clinfo` key determines how the command is assembled.

If the path is relative, it is resolved under `PLAINBOX_PROVIDER_DATA`.

**Format:**

```json
{
  "clinfo": {
    "LD_PATH": ["/path/to/lib1", "/path/to/lib2"],
    "env1": "value1"
  }
}
```

- `LD_PATH` prepends entries to `LD_LIBRARY_PATH` before the command is run.
- Any other key/value pair is prepended as an environment variable assignment.
- If the `clinfo` key is absent from the file, the default system `clinfo` is
  used unchanged.

### `CLINFO_VALIDATION_JSON_FILE`

Points to a JSON file with two optional sections: `ignored_set` and
`customized_validation_set`.

**Format:**

```json
{
  "ignored_set": {
    "<Platform Name>": ["<Device Name 1>", "<Device Name 2>"]
  },
  "customized_validation_set": {
    "<Platform Name>": {
      "<Device Name>": {
        "<CL_PROPERTY>": "<expected value>"
      }
    }
  }
}
```

- `ignored_set` — platform/device pairs listed here will have `ignore: true`
  in the resource output and will not produce validation jobs.
- `customized_validation_set` — extends (not replaces) the default validation
  set for a specific platform/device pair. Properties defined here are added
  to the three default properties that are always validated.

**Example:**

```json
{
  "ignored_set": {
    "ARM Platform": ["FooBar 9999"]
  },
  "customized_validation_set": {
    "ARM Platform": {
      "Mali-G57 r0p0": {
        "CL_DEVICE_MAX_COMPUTE_UNITS": "2",
        "CL_DEVICE_MAX_WORK_GROUP_SIZE": "512",
        "CL_DEVICE_VENDOR_ID": "0x13b5"
      }
    }
  }
}
```

In this example:

- The `ignored_set` entry causes the pair platform `ARM Platform` / device
  `FooBar 9999` to be skipped. The resource job emits `ignore: true` for that
  pair, so the template does not generate a validation job for it.
- The `customized_validation_set` entry extends the validation for platform
  `ARM Platform` / device `Mali-G57 r0p0`. In addition to the three default
  properties (`CL_DEVICE_AVAILABLE`, `CL_DEVICE_COMPILER_AVAILABLE`,
  `CL_DEVICE_EXECUTION_CAPABILITIES`), the validation job also checks
  `CL_DEVICE_MAX_COMPUTE_UNITS`, `CL_DEVICE_MAX_WORK_GROUP_SIZE`, and
  `CL_DEVICE_VENDOR_ID` against the values defined here.

## Running the jobs

After setting the manifest and environment, run the automated graphics plan:

```bash
checkbox-ce-oem.checkbox-cli run com.canonical.contrib::ce-oem-graphics-automated
```

The detect job uses `clinfo_test.py detect` to confirm at least one
platform/device pair is available. The resource job uses
`clinfo_test.py resource` to generate per-pair records. Each generated
validation job uses `clinfo_test.py test` to query and compare device
properties against the expected values.

A job fails if `clinfo` cannot be executed, no OpenCL platform or device is
found, a queried property is missing from the output, or a property value does
not match the expected value.
