# NVIDIA CUDA samples test suite

Runs every test from NVIDIA's [cuda-samples] repository as its own
Checkbox job, on any device with an NVIDIA GPU (Jetson/Tegra boards
included).  Jobs are generated by the `cuda_samples_resource` resource
job and named `cuda-sample/<samples-category>-<sample>`, e.g.
`cuda-sample/0_Introduction-deviceQuery`.

Test plan: `cuda-samples-automated`.
Manifest gate: `has_nvidia_cuda`.

[cuda-samples]: https://github.com/NVIDIA/cuda-samples

## Prebuilt-only

Checkbox never clones or builds cuda-samples.  The tree must be cloned
**at the tag matching the installed CUDA version** and built before
Checkbox runs:

- **Classic**: provisioning (or the operator) clones and builds the
  tree, conventionally at `/opt/nvidia/cuda-samples` (NVIDIA's Jetson
  BSP layout).  Any other location works via `CUDA_SAMPLES_PATH`.
- **Ubuntu Core**: the cuda-samples snap ships the prebuilt tree and
  must expose it at `/snap/<name>/current/cuda-samples` — the layout
  this suite auto-discovers.

The `cuda/samples-readiness` job fails the whole suite early when the
tree is missing, contains no built binaries, or (for git checkouts) is
not checked out at the newest cuda-samples tag lower than or equal to
the CUDA version reported by `nvidia-smi` — e.g. CUDA 12.6 expects tag
`v12.5` because the tags jump from v12.5 to v13.0.  Snap-shipped trees
carry no git metadata; their version match is guaranteed at snap build
time instead.  The tag comparison can only see the tags present in the
clone, so provisioning should keep the clone tag-complete (a
`--depth 1` clone hides newer tags from the check); rebuild from a
clean tree when re-provisioning at a different tag, or stale binaries
from the previous build may linger.

A sample that is present in the tree but has no built binary is *not*
a failure: `make -k`/cmake legitimately skip samples whose platform
dependencies are missing, so such samples are reported as visible
skips with reason `not built` (see below).

Each sample executes in a **disposable sandbox** — a temporary copy of
the sample's directory (with `Common/` symlinked beside it), so
samples that write output files work rootless even when the tree is
root-owned, and a test run never modifies the provisioned tree.

## Environment variables

| Variable | Meaning | Default |
|---|---|---|
| `CUDA_SAMPLES_PATH` | Root of the prebuilt cuda-samples tree | `/opt/nvidia/cuda-samples`, then `/snap/*/current/cuda-samples` |
| `CUDA_SAMPLES_TIMEOUT` | Per-sample timeout in seconds (some EGL/GLES samples render forever on headless systems) | `300` |
| `CUDA_SAMPLES_EXCLUDE_FILE` | Exclude-jobs JSON file override | `$PLAINBOX_PROVIDER_DATA/cuda/exclude_jobs.json` |

## Excluding samples — visible skips

Samples that cannot run on a device family live in an exclude-jobs
JSON file (`data/cuda/exclude_jobs.json`, described by
`exclude_jobs.schema.json` next to it; the runner enforces the same
shape when loading).  Excluded samples are **still listed** by the
resource job, with `skip: True` and the reason, and their generated
jobs fail their `requires` gate — so every sample shows up in the
results as either run or skipped, never silently missing.  Samples
with no built binary are skipped the same way with reason
`not built`.

Example entry:

```json
{
    "excludes": [
        {
            "name": "deviceQuery",
            "category": "0_Introduction",
            "reason": "Example: category is optional, name is exact"
        }
    ]
}
```

A project can select a list shipped in the provider data dir by bare
name, or ship its own file and point at it by absolute path:

```ini
[environment]
# a shipped list (resolved in the provider's data/cuda/):
CUDA_SAMPLES_EXCLUDE_FILE = exclude_jobs.jetson.json
# or a project-specific file:
# CUDA_SAMPLES_EXCLUDE_FILE = /path/to/project-excludes.json
```

The shipped default (`exclude_jobs.json`) contains only universal
excludes: multi-GPU/P2P samples, EGL/GLES samples that hang on
headless systems, and tools that are not self-contained tests.
`exclude_jobs.jetson.json` adds the Jetson-specific exclusions from
NVIDIA's Jetson reference runner (`run-cuda-samples.py`): the cuDLA
samples and the per-CUDA-release excludes — those fail on Jetson/L4T
but the per-release ones run fine on other NVIDIA platforms, so
Jetson projects must select that list in their launcher.

### Starting from a shipped list: `include`

A list can start from ONE shipped base list instead of copying its
entries, with the top-level `include` key:

```json
{
    "include": "exclude_jobs.json",
    "excludes": [
        {"name": "myProjectSample", "reason": "why it cannot run here"}
    ]
}
```

The rules are strict so the effective list is always easy to trace:

- `include` takes a **bare file name** (no path), found only in the
  provider's `data/cuda/` directory — `exclude_jobs.json` always
  means the shipped default, on every machine.
- Only **one** include, and the included file must not use `include`
  itself — no chains. The full list is always at most two files.
- The same `name` + `category` in both files is an **error**; there
  is no overwrite. Every entry has exactly one definition.

`exclude_jobs.jetson.json` itself uses this: it holds only the
Jetson-specific entries plus `"include": "exclude_jobs.json"`.  Every exclude entry needs a reviewed reason;
do not add entries for failures that have not been diagnosed.

## Rootless

All jobs run as the normal test user — none use `user: root`.  On
Tegra, the CUDA device nodes (`/dev/nvmap`, `/dev/nvhost-*`, ...) are
root-only by default; grant access with udev `uaccess` rules plus a
logind seat for the test user (see OEMQA-6849 for the recipe) rather
than running the tests as root.
